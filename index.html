CLAUDE.md וקבצי ההוראות

קבצי CLAUDE.md הם קבצי Markdown שאתם כותבים, ו-Claude קורא אותם בתחילת כל סשן. הם הנחיה, לא אכיפה: Claude קורא אותם כהקשר, אבל אין מנגנון שמבטיח שהוא יציית. להתנהגות מובטחת משתמשים ב-hooks או ב-permissions (פרק ההגדרות).

איך הטעינה עובדת בפועל

  • בהפעלה נטענים ‎CLAUDE.md ו-‎CLAUDE.local.md מתיקיית העבודה וכל התיקיות מעליה. הרצה מתוך ‎foo/bar/ טוענת גם את ‎foo/CLAUDE.md.
  • הקבצים מחוברים זה לזה (concatenated), לא דורסים זה את זה. בסדר: משורש מערכת הקבצים ועד תיקיית העבודה; בתוך אותה תיקייה, ‎CLAUDE.local.md נקרא אחרון.
  • קבצי ‎CLAUDE.md בתתי-תיקיות נטענים רק כש-Claude קורא קבצים שם - לא בהפעלה.
  • כשהוראות מתנגשות, הוראת פרויקט גוברת על הוראה גלובלית.
  • הערות HTML ברמת בלוק (‎<!-- ... -->) מוסרות לפני ההזרקה לקונטקסט - אפשר לכתוב הערות למתחזקים אנושיים בלי לבזבז tokens.

ייבוא קבצים עם ‎@

בתוך CLAUDE.md אפשר לייבא קבצים נוספים עם ‎@path/to/file. יחסי לקובץ שבו כתוב הייבוא, רקורסיבי עד עומק 4. ייבוא חיצוני (נתיב מחוץ לתיקיית העבודה, למשל ‎@~/.claude/my-instructions.md) מציג דיאלוג אישור בפעם הראשונה בפרויקט. כדי לציין נתיב בלי לייבא, עטפו ב-backticks.

כללי עבודה מומלצים

  • עד 200 שורות לקובץ. קבצים ארוכים נטענים במלואם אבל פוגעים בדיוק הביצוע. גדל מעבר? מפצלים ל-rules (מיד).
  • /init מייצר CLAUDE.md התחלתי מהקוד. /memory פותח את הקובץ לעריכה מתוך סשן. /context מראה אילו קבצי זיכרון באמת נטענו.
  • כותבים את מה שהייתם מסבירים שוב ושוב: פקודות build/test/lint, קונבנציות, מבנה. מה שרלוונטי רק למשימות מסוימות - עובר ל-skill או ל-rule.

.claude/rules/ - הוראות נושאיות, אופציונלית לפי נתיב

תיקיית ‎.claude/rules/ (וגם ‎~/.claude/rules/) מחזיקה הוראות מפוצלות לפי נושא. rule בלי paths: ב-frontmatter נטען בכל הפעלת סשן כמו CLAUDE.md; rule עם ‎paths: נטען רק כש-Claude קורא קובץ שמתאים ל-glob. זו הדרך להחזיק קונבנציות של frontend ו-backend באותו repo בלי לנפח את הקונטקסט של שתיהן.

---
paths:
  - "**/*.test.ts"
  - "**/*.test.tsx"
---

# Testing Rules
- Use descriptive test names
- Mock external dependencies, not internal modules
  • תתי-תיקיות מתגלות אוטומטית: ‎.claude/rules/frontend/react.md עובד.
  • חוק ברמת משתמש (‎~/.claude/rules/) חל על כל הפרויקטים.
  • במונו-repo רועש: ‎claudeMdExcludes מדלג על קבצי CLAUDE.md של צוותים אחרים.

קבצי ההגדרות: settings.json וחבריו

בניגוד ל-CLAUDE.md, קבצי settings נאכפים: הרשאות, hooks ומשתני סביבה פועלים בין אם Claude "מסכים" ובין אם לא.

קדימויות, מהגבוה לנמוך: Managed → ארגומנטים בשורת הפקודה (‎--settings, ‎--permission-mode) → ‎settings.local.json → ‎.claude/settings.json → ‎~/.claude/settings.json. מפתח ברמה גבוהה דורס את אותו מפתח למטה. משתני סביבה הם לא רמה בסדר - לכל צד משתנה/מפתח כלל משלו (ראו env vars reference). הגדרה ארגונית גוברת כמעט תמיד - גם על ‎--settings; היוצא דופן המרכזי: ‎model ארגוני קובע את ברירת המחדל אבל עדיין אפשר להחליף ב-‎/model, והנעילה האמיתית היא ‎availableModels.

  • הרשאות שאתם מאשרים בתוך סשן ("allow always") נשמרות ב-‎.claude/settings.local.json.
  • מערכים כמו ‎permissions.allow מתאחדים בין הרמות; סקלרים כמו ‎model נלקחים מהרמה הספציפית ביותר.
  • מה שמכניסים: ‎permissions (allow/deny/ask), ‎hooks, ‎env, ‎model, ‎statusLine, ‎outputStyle ועוד.

~/.claude.json local only

מצב אפליקציה, לא הגדרות: theme, סשן OAuth, החלטות trust לכל פרויקט (מפתח ‎projects), טוגלים של IDE (‎autoConnectIde), ושרתי ה-MCP האישיים שלכם. בדרך כלל מנהלים דרך ‎/config ולא עורכים ידנית. גיבויים אוטומטיים של הקובץ נשמרים ב-‎~/.claude/backups/ (חמשת האחרונים).

~/.claude/keybindings.json local only

קיצורי מקלדת מותאמים ל-CLI. ‎/keybindings פותח את הקובץ עם schema. נטען בהפעלה ומתרענן חם בעריכה. Ctrl+C, Ctrl+D, Ctrl+M ו-Caps Lock שמורים ולא ניתנים לשיבוץ מחדש.

ההרחבות: skills, commands, agents, output-styles, workflows

כל ההרחבות קיימות בשתי רמות: ‎.claude/ בפרויקט (משותף לצוות) ו-‎~/.claude/ (אישי, בכל הפרויקטים). פורמט זהה, היקף שונה.

skills/<name>/SKILL.md committed בפרויקט

פרומפט לשימוש חוזר שמופעל ב-‎/skill-name או אוטומטית כש-Claude מזהה התאמה. כל skill הוא תיקייה: ‎SKILL.md ולצדו קבצי עזר (templates, checklists, סקריפטים) ש-Claude קורא on-demand - נתיב תיקיית ה-skill זמין לו, ובסקריפטים משתמשים ב-‎${CLAUDE_SKILL_DIR}.

מתי נטען: בהקלדת /name, או כשה-description ב-frontmatter מתאים למשימה.

שליטה ב-frontmatter: ‎disable-model-invocation: true (רק אתם מפעילים), ‎user-invocable: false (מוסתר מהתפריט אבל Claude יכול). ארגומנטים: ‎$ARGUMENTS, ‎$0, ‎$1. שורת ‎!`command` מריצה פקודת shell ומזריקה את הפלט לפרומפט לפני שהמודל רואה אותו.

commands/*.md committed בפרויקט

פרומפטים חד-קובציים שמופעלים ב-‎/name. אותו מנגנון בדיוק כמו skills - ‎commands/deploy.md יוצר את ‎/deploy בדיוק כמו ‎skills/deploy/SKILL.md, ושניהם יכולים לעלות אוטומטית. ההבדל: skill הוא תיקייה ולכן יכול לאגוד קבצי עזר. אם קיימים skill ו-command באותו שם - ה-skill מנצח. לדברים חדשים: כותבים skills; commands נשאר נתמך.

agents/*.md committed בפרויקט

כל קובץ מגדיר subagent: system prompt משלו, גישת כלים משלו (‎tools:), ואופציונלית מודל משלו. רץ בחלון קונטקסט נפרד, כך שהשיחה הראשית נשארת נקייה. ה-‎description קובע מתי Claude מעביר אליו משימות אוטומטית; אפשר גם להקיש ‎@ ולבחור אותו. דוגמה קלאסית: reviewer עם ‎tools: Read, Grep, Glob - יכול לבדוק אבל אף פעם לא לערוך.

output-styles/*.md בדרך כלל אישי

סט הוראות שמשנה איך Claude עובד - ובברירת מחדל גם מחליף את הוראות הנדסת-התוכנה המובנות (‏‎keep-coding-instructions: true משאיר אותן). בוחרים עם ‎/output-style או מפתח ‎outputStyle ב-settings. בדרך כלל אישי (‎~/.claude/output-styles/); שמים בפרויקט רק סגנון שהצוות חולק. סגנון פרויקט באותו שם גובר על אישי.

workflows/*.js

סקריפטים של dynamic workflows שמתזמרים הרבה subagents - נכתבים על ידי Claude ונשמרים מתוך ‎/workflows (מקש ‎s), לא נכתבים מאפס. כל קובץ הופך לפקודת ‎/name. workflow של פרויקט גובר על אישי באותו שם.

agent-memory/<agent-name>/MEMORY.md Claude writes

זיכרון מתמשך ל-subagents - נפרד מה-auto memory של הסשן הראשי. נוצר רק לסוכנים עם ‎memory: ב-frontmatter: ‎memory: project כותב ל-‎.claude/agent-memory/ (משותף ב-git), ‎memory: local ל-‎.claude/agent-memory-local/ (מחוץ ל-git), ו-‎memory: user ל-‎~/.claude/agent-memory/ (חוצה פרויקטים). הסוכן כותב ומתחזק את הקובץ בעצמו; 200 השורות הראשונות (עד 25KB) נטענות ל-system prompt שלו בכל ריצה.

~/.claude/plugins/

Plugins מותקנים, marketplaces משובטים, רישום ההתקנות ‎installed_plugins.json ונתוני plugin - מנוהל על ידי פקודות ‎claude plugin. Plugins שמסונכרנים מחשבון claude.ai יורדים ל-‎plugins/synced/. אל תערכו ידנית.

שני קבצי פרויקט נוספים בשורש

.worktreeinclude committed

רשימת קבצים מ-gitignore (בתחביר ‎.gitignore) ש-Claude Code מעתיק לכל worktree חדש שהוא יוצר (‎--worktree, subagent עם ‎isolation: worktree). בלעדיו, worktree הוא checkout נקי - בלי ‎.env, בלי סודות מקומיים. רק קבצים שגם מתאימים לתבנית וגם מ-gitignored מועתקים.

נתוני סשן ואפליקציה: מה Claude Code כותב תוך כדי עבודה

מעבר לקבצים שאתם כותבים, ‎~/.claude/ מחזיק את מה שהכלי עצמו כותב. כל אלה טקסט גלוי, לא מוצפן - הרשאות הקבצים של מערכת ההפעלה הן ההגנה היחידה. כל דבר שעובר דרך כלי - תוכן קובץ, פלט פקודה, טקסט שהודבק - נכתב ל-transcript על הדיסק.

Transcripts - ‎projects/<project>/<session>.jsonl

כל סשן נשמר רציף כ-JSONL: כל הודעה, כל קריאת כלי, כל תוצאה. ‎<project> הוא נתיב תיקיית העבודה עם תווים לא-אלפאנומריים שהוחלפו ב-‎- (שם ארוך מדי נחתך ל-200 תווים + hash). זה מה שמאפשר ‎claude --continue, ‎--resume והבורר ‎/resume.

  • מה אפשר לעשות איתם: להמשיך סשן אחרי יציאה (‎claude -c), לענף סשן (‎/branch מעתיק את ה-transcript), לייצא (‎/export לקריאה אנושית), לקרוא את ‎transcript_path בתוך hook או status line, ולארכב ב-‎SessionEnd hook.
  • ‎subagents/ תחת תיקיית הסשן: transcripts של subagents; ‎tool-results/: פלטים גדולים שהופנו לקבצים נפרדים ותמונות מ-MCP.
  • קבצי ‎.orphaned-*.jsonl ו-‎.superseded-*: גרסאות קודמות שהכלי שם בצד במקום לדרוס; לא מופיעים בבורר הסשנים.
  • שליטה בשם תיקיית הפרויקט: ‎CLAUDE_CODE_PROJECT_DIR_NAME (יחד עם ‎CLAUDE_CONFIG_DIR, דורש v2.1.234+).

Transcripts של Claude Desktop ו-Cowork נשמרים ללא הגבלת גיל אלא אם מגדירים ‎desktopSessionCleanupPeriodDays (v2.1.248+). ה-sweep מושהה ב-‎--bare וכשאי אפשר לקבוע בטוח את תקופת השמירה.

תיקיית ה-scratchpad

לכל סשן יש תיקיית עבודה זמנית משלו (קבצי ביניים, סקריפטים, טיוטות) - כש-Claude אומר "שמרתי ב-scratchpad", זה שם. נמצאת תחת תיקיית temp, לא תחת ‎~/.claude: לינוקס ‎/tmp/claude-<uid>/<project>/<session-id>/scratchpad/ (או תחת ‎$TMPDIR/‎CLAUDE_CODE_TMPDIR), macOS ‎/private/tmp/claude-<uid>/..., ו-Windows ‎%TEMP%\claude\.... Hooks מקבלים את הנתיב כ-‎scratchpad_dir. היא נמחקת עם ה-transcript של הסשן, ומערכת ההפעלה עלולה לפנות temp מוקדם יותר - דבר שצריך להישאר? בקשו מ-Claude להעביר לפרויקט.

אזהרת אבטחה: הכל טקסט גלוי

אם כלי קרא קובץ ‎.env או פקודה הדפיסה סוד - הערך נכתב ל-‎projects/<project>/<session>.jsonl. להקטנת החשיפה: להוריד את ‎cleanupPeriodDays, להגדיר ‎CLAUDE_CODE_SKIP_PROMPT_HISTORY לדילוג על כתיבת transcripts והיסטוריה (במצב לא-אינטראקטיבי: ‎--no-session-persistence לצד ‎-p), ולהשתמש ב-permission rules כדי לחסום קריאת קבצי credentials.

ניקוי ומחיקה: ‎claude project purge

הפקודה ‎claude project purge מוחקת את כל מה שהכלי שומר על פרויקט אחד:

  • Transcripts ו-auto memory תחת ‎projects/
  • רשומות ‎tasks/, ‎debug/ ו-‎file-history/ של הסשנים
  • שורות הפרויקט ב-‎history.jsonl
  • רשומת הפרויקט ב-‎~/.claude.json

היא לא נוגעת ב-‎shell-snapshots/, ‎backups/, ובתמונות/scratchpad שבתיקיית temp. הפקודה מדפיסה תוכנית מחיקה מלאה ומבקשת אישור לפני שמוחקת כלום:

# תצוגה מקדימה בלי מחיקה
claude project purge ~/work/my-repo --dry-run

# מחיקה עם אישור
claude project purge ~/work/my-repo

# בלי אישור (לסקריפטים) · כל הפרויקטים · שלב אחד בכל פעם
claude project purge ~/work/my-repo --yes
claude project purge --all
claude project purge ~/work/my-repo -i
